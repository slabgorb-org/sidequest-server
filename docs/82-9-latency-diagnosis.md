The 71-40 hypothesis is confirmed and sharpened. Three findings:

1. **The decompose stall is real and entirely the SDK round-trip — not our
   code.** Mean decompose is **4.1s** (p95 **6.6s**) against the ADR-113 `<1.2s`
   budget — 3–5× over. The `sdk_latency_ms` split shows **~100%** of that time is
   the raw Haiku `emit_tool` round-trip; the prompt-assembly remainder
   (`latency_ms − sdk_latency_ms`) is **0.1ms**. So there is *no* code hot-spot in
   `IntentRouter.decompose` itself to optimize — the wall-clock is the model call.

2. **But the code lever is the prompt SIZE, not the prompt code.** The router
   ships a mean **48,744-byte** (~48 KB) `state_summary` every call, and
   `state_summary_bytes` correlates **0.50** with total decompose latency. A 48 KB
   summary inflates input tokens on every Haiku call, which is what makes the
   "env" round-trip long. The actionable fix is therefore *input slimming*
   (ADR-110 snapshot slimming / allowlist pruning), **not** rewriting the decompose
   timing path. Env dominates the clock; code (summary size) feeds the env cost.

3. **Tool-loop depth is NOT the driver of the 23s turn.** Turns averaged **2.57**
   iterations (max 3, zero loop-exceeded), and `iterations_used` correlates only
   **0.18** with whole-turn wall-clock. The **~23s** `narration.turn` p50 is the
   narration model generating long prose, not a runaway tool loop. The new
   raise-path `loop_exceeded` marker fired on 0 turns here — healthy — and is now
   in place to catch the worst-case turns when they do occur.

**Recommended next work (not this story):** an input-slimming pass on the router
`state_summary` (target 48 KB → a few-KB allowlist) is the single highest-leverage
latency fix; it attacks both the decompose p95 and the per-call token cost. The
`narrator.tool_loop` cap toggle (`SIDEQUEST_NARRATOR_ITERATION_CAP`, shipped here)
is available if a future world shows runaway loops, but this capture shows loops
are not currently the bottleneck.
